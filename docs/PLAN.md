# Arukone: Ship-Ready Plan

## Context

Arukone is a working Vite + React + TypeScript puzzle game. The code is migrated and polished (Phases 1-5), but the project lacks production infrastructure: no tests, no CI, no releases, no deployment config, and the repo has leftover files from the original prototype. This plan takes it from "works on my machine" to "deployed, tested, versioned, and maintainable."

Domain: `arukone.play.example.com` (placeholder; real domain in private project memory)

### Phase 1: Security Hardening — pre-deployment gate

**Goal:** Eliminate all external dependencies and add security tooling. This is the gate before anything goes public.

#### 1a. Self-host fonts
- Download DM Sans + JetBrains Mono `.woff2` files → `public/fonts/`
- Replace Google Fonts `@import` in `index.css` with local `@font-face`
- **Why:** Google Fonts sends visitor IPs to Google (GDPR concern), and it's the only external network dependency. Self-hosting enables true offline PWA and removes a tracking vector.

#### 1b. ESLint security plugin
- Add `eslint-plugin-no-unsanitized` (Mozilla, actively maintained)
- Catches: `innerHTML`, `document.write`, `insertAdjacentHTML`, `outerHTML`
- High signal for a React SPA; skip `eslint-plugin-security` (Node.js-focused, low value here)
- Add to `eslint.config.js`, runs as part of existing `bun run lint`

#### 1c. Dependency audit in CI
- `bun audit --audit-level=high` — native to Bun (since v1.2.15), reads `bun.lock`
- Fails CI on high/critical CVEs
- No need for `npm audit` fallback

#### 1d. Security headers
For the Cloudflare Worker (when deployed), add headers:
```
Content-Security-Policy: default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
```
These can be set via a minimal Worker script or `_headers` file (Cloudflare supports both).

#### 1e. Full security review
- Verify no source maps in production build (`build.sourcemap` in vite.config.ts — default is false, confirm)
- Verify `dist/` contains no external resource references
- Check for any dynamic code patterns (eval, Function, setTimeout with strings)
- Verify localStorage data is non-sensitive (game stats only)
- Run `bun audit`, review all dependencies

**Findings from initial review (already done):**
- No API calls, no forms, no user text input
- No innerHTML, dangerouslySetInnerHTML, eval, Function()
- Only external resource: Google Fonts (removed in 1a)
- All dependencies clean (React 19, Vite 8, Tailwind 4, ESLint)
- localStorage stores only play stats (non-sensitive)

### Phase 2: PWA — installable, offline-capable

**Goal:** Users can install the game on their home screen and play offline.

#### What is a PWA?

A Progressive Web App adds three capabilities to a regular website:
1. **Installable** — home screen icon, full-screen standalone mode, splash screen. No app store needed. Users tap "Add to Home Screen" in their browser.
2. **Offline-capable** — a service worker caches all assets after first visit. The game works without internet.
3. **Native-feeling** — no browser chrome (address bar, tabs), iOS status bar integration, app-like transitions.

For Arukone this is ideal: the game is self-contained (no API calls), all 800 puzzles are bundled in the app, and the target audience plays on mobile devices.

#### Implementation

**Dependency:** `vite-plugin-pwa` (uses Google's Workbox under the hood)

**How it works:**
- At build time, the plugin generates a service worker that pre-caches all static assets (JS, CSS, HTML, JSON, fonts, icons)
- On first visit, the browser downloads everything and stores it in Cache Storage
- On subsequent visits (even offline), the service worker intercepts requests and serves from cache
- `registerType: 'autoUpdate'` means new versions activate automatically — no "update available" prompt needed for a game

**Files:**
| File | Action | Purpose |
|------|--------|---------|
| `vite.config.ts` | modify | Add `VitePWA()` plugin config |
| `index.html` | modify | iOS meta tags (Apple doesn't fully support the manifest spec) |
| `public/icons/icon-192.png` | create | Android install icon + PWA |
| `public/icons/icon-512.png` | create | Android splash + maskable icon |
| `public/icons/apple-touch-icon.png` | create | iOS home screen (180px) |

**iOS meta tags** (required because Safari ignores parts of the standard manifest):
```html
<meta name="apple-mobile-web-app-capable" content="yes">
<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent">
<link rel="apple-touch-icon" href="/icons/apple-touch-icon.png">
```

**Persistence migration:** Current `usePersistence.ts` already uses `localStorage` (verified in code review). No migration needed.

### Phase 3: Deployment — Cloudflare Workers with Static Assets

**Goal:** Merge to main → auto-deploys to `arukone.play.example.com`.

#### Why Cloudflare Workers (not Pages)

Cloudflare Pages was deprecated in April 2025. The `cloudflare/pages-action` GitHub Action is officially deprecated. **Cloudflare Workers with Static Assets** is the replacement:
- Serves static files from 300+ edge locations globally
- Built-in SPA routing: `not_found_handling: "single-page-application"` — returns `index.html` for all routes with 200 status
- Free tier: 100k requests/day, unlimited bandwidth
- Actively maintained, the only path forward for new projects

#### Local validation (no remote staging needed)

| Tool | What it tests | When to use |
|------|---------------|-------------|
| `vite dev` | Hot-reload during development | While coding |
| `vite preview` | Built output as plain static server | Quick build check |
| `wrangler dev` | **Full Cloudflare Workers runtime (workerd) locally** | Pre-deploy validation |
| `wrangler deploy --dry-run` | Config validation without deploying (no credentials needed) | CI on PRs |

`wrangler dev` is the authoritative local test — it runs the actual Workers runtime, honors `not_found_handling`, and behaves identically to production. This eliminates the need for a remote staging environment.

**CI validates production-readiness:**
- PRs: lint + typecheck + test + build + `wrangler deploy --dry-run` (validates config, no deploy)
- Main: lint + typecheck + test + build + `wrangler deploy` (actual deploy)

#### Configuration

**`wrangler.jsonc`:**
```jsonc
{
  "$schema": "https://schema.cloudflare.com/wrangler.json",
  "name": "arukone",
  "compatibility_date": "2025-04-01",
  "assets": {
    "directory": "./dist",
    "not_found_handling": "single-page-application"
  }
}
```

No server-side Worker code needed — this config serves `dist/` as static assets with SPA fallback.

#### CI deploy job (added to existing workflow)
```yaml
deploy:
  needs: build
  if: github.ref == 'refs/heads/main'
  steps:
    - uses: cloudflare/wrangler-action@v3
      with:
        command: deploy
        wranglerVersion: "4"  # pinned major
      env:
        CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
        CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
```

**Secrets (scoped, least privilege):**
- `CLOUDFLARE_API_TOKEN` — create a scoped token with Workers permission only (not global API key)
- `CLOUDFLARE_ACCOUNT_ID` — your Cloudflare account ID

#### Custom domain setup (one-time, manual)
1. Cloudflare dashboard → Workers & Pages → arukone → Settings → Domains & Routes
2. Add custom domain: `arukone.play.example.com`
3. If your zone is already on Cloudflare, CNAME is added automatically
4. SSL is automatic and free

## Development Workflow (Day-to-Day)

After Phase 0 is complete, this is how coding works:

```
1. Pick work       →  Check issues/backlog, or /dc:ideate for new work
2. Branch          →  git switch -c feat/thing from up-to-date main
3. Develop         →  mise run dev (hot-reload, exposed to local network)
4. Verify locally  →  mise run check (lint + typecheck)
                      mise run test (vitest)
5. Commit          →  /dc:commit (conventional commit with trailer)
6. Push + PR       →  git push -u origin HEAD → gh pr create
7. CI validates    →  lint, typecheck, test, build, audit, wrangler dry-run
8. Merge           →  Squash merge to main → auto-deploys to arukone.play.example.com
9. Release         →  /dc:ship patch|minor when ready to cut a version
```

### Versioning (semver)

| Phase | Range | Bump rules |
|-------|-------|------------|
| Pre-launch | `0.1.0` → `0.x.y` | minor = features, patch = fixes. Breaking changes OK. |
| Launch | `1.0.0` | PWA, deployed, device-tested |
| Post-launch | `1.x.y` | Standard semver. Major = breaking, minor = features, patch = fixes. |

### When to release
- After completing a logical milestone (not every commit)
- Pre-launch: release freely after each phase
- Post-launch: group related changes into releases

## Deployment Alternatives (for reference)

| Option | Best for | Trade-off |
|--------|----------|-----------|
| **Cloudflare Workers** (chosen) | Production — free, fast, custom domain on existing tenant | Requires GitHub secret setup |
| **Vercel** | Quick deploy, auto-detects Vite | 100GB/mo cap, no existing tenant |
| **Tailscale Serve** | Private sharing on tailnet | Only Tailscale devices |
| **Tailscale Funnel** | Ad-hoc public demo | Machine must be on, no CDN, no custom domain |
| **Self-hosted** | Full control | You manage TLS, uptime, updates |

Tailscale Funnel remains useful as an ad-hoc demo tool: `tailscale funnel 5173` shares the dev server instantly.
